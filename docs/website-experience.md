# 沉浸式滾動敘事

訪客要看得懂誰正在做什麼、為何受阻，以及自己的操作改變了什麼。同一張圖一路放大、
更換標語或重複淡入，只能算視覺效果；要求故事體驗時，不能以此交付完成。

## 先寫因果，再寫分幕

在 `design-brief.md` 用一句話連起：**主角 → 目標 → 阻力 → 訪客行動 → 後果 → 解決 → CTA**。
主角可以是人物、物件、產品或訪客；阻力也可以是距離、資訊不足、選擇與製作過程，
不必硬加反派。故事承諾要能在終幕兌現，CTA 承接剛理解或完成的事情。

先回答七個具體問題，已知答案不再問使用者：

1. 主角是誰？跨場景用哪個外觀或標記讓人認得？
2. 他／它想抵達、取得或改變什麼？訪客為何在意？
3. 哪件事讓目標無法立刻完成？
4. 訪客能做什麼？自然捲動可以推進旅程，額外選項必須有可理解的用途。
5. 做了以後，畫面、路徑、物件狀態或結果實際改變什麼？
6. 終幕如何讓人看見目標已完成，或理解未完成的原因？
7. 看商品、詢問、分享或重玩，哪個行動自然接續這個結果？

將完整故事示範拆成至少四個有因果的節拍，用作技能範例與回歸驗收。一般專案的幕數、
題材與長度依需求調整；短版可以合併節拍，長版可以增加場景，不為湊數拉長捲動距離。
四張不同風景若彼此沒有狀態交接，仍不足以證明故事成立。

| 節拍例 | 入幕狀態 → 出幕狀態 | 畫面必須讓人看見 | 接下一幕的原因 |
|---|---|---|---|
| 目標出現 | 主角在原點 → 主角開始前往目的地 | 主角、目的地線索與一次有方向的移動 | 已出發，需要穿越下一個空間 |
| 阻力發生 | 路徑暢通 → 主角受阻或發現新條件 | 環境／前景改變路徑，或資訊改變選擇 | 原做法無法直接達成目標 |
| 行動產生後果 | 面對選擇 → 路徑或主角狀態改變 | 操作與可見反應對得上，下一幕承接此狀態 | 新條件使目標可以繼續 |
| 解決與行動 | 抵達 → 結果穩定、可採取下一步 | 主角與目的地建立關係，結果文案和 CTA 一致 | 訪客可購買、詢問或完成體驗 |

這是因果檢查範例，不是每站套同一個情節。另記錄色票、字體角色與 fallback、字級、
間距和品牌專屬視覺特徵；畫面風格須服務這個故事。

## 每幕要有可實作的狀態契約

先寫 `storyboard.md`，或在 `design-brief.md` 加同等內容；不要只列「電影感、視差、縮放」。

```text
幕 ID／敘事職責：[此幕必須使訪客理解的改變]
前因／主角目標：[承接上一幕的哪個結果]
入幕狀態：[場景、主角位置／朝向／尺度／持物、已知資訊與互動狀態]
素材：[背景 ID、主角 ID／變體、前景遮擋 ID、效果層；HTML 文字與 CTA]
進度：[本幕相對進度 0..1；進入、轉折、結果的觸發範圍]
動作：[誰沿哪條路徑移動；誰遮擋誰；何時切場；不只寫鏡頭 zoom]
訪客操作／後果：[按鈕或選項如何改變可見狀態；略過時的預設路徑]
出幕狀態／下一幕承接：[位置、身份、物件、資訊與結果如何銜接]
倒帶：[捲回前幕如何重建；哪些使用者選擇保留；重玩如何重設]
替代：[手機、減少動態、無 JS 時，哪張靜態圖與文字表達同一件事]
驗收畫面：[入幕、轉折、結果的預期畫面；可辨識的失敗條件]
```

位置宜用場景座標或百分比，避免依賴單一視窗像素。跨幕共用主角時保持身份與運動方向；
換朝向、變形、出入畫、日夜或場景跳接需在分鏡交代。背景可切換，主角與環境仍要有
前後景、接觸、遮擋或明確視覺關係，不能只像滑過四張海報的貼圖。

把敘事狀態和顯示效果分開：章節進度決定目前情節，選項決定可重現的分支，
transform／opacity 只負責呈現。跳章、快速下捲及倒捲後，要能由當下進度重建完整畫面，
不能依賴先前曾觸發一次的 class、計時器或入幕事件才成立。

## 訪客參與要有後果，也能略過

選擇只有在改變路徑、比較內容、物件狀態或結果時才保留；改完下一幕仍完全相同的按鈕
不算敘事互動。結果文字必須與畫面一致，並提供清楚的重選／重玩方式。

主線提供合理預設路徑；不操作仍可理解故事並完成主要任務。不要以未玩遊戲、未授權聲音
或未看完動畫為由阻擋價格、商品資訊與 CTA。體驗中的選擇不等於下單或同意收款；
真實交易仍依商務流程處理。

## 實作選擇

- 靜態 `<picture>` 作可見基線；圖片有 width／height 或 aspect-ratio。
- 大螢幕可用 sticky 畫面配自然捲動章節。以相對容器進度控制景深、位移、縮放或透明度，
  往上捲動可自然倒帶。不要以全頁 scrollY 硬編每幕像素位置。
- IntersectionObserver 控制接近畫面的素材載入；連續動畫採單一 requestAnimationFrame，
  不可見時停止。不要預載全部高解析圖序列。
- 原生 scroll-driven animations 做 feature detection；不支援則靜態或輕量 JS fallback。
  大型 3D／影片不是預設，需要用途、載入預算與圖片替代。
- 每個圖層與動效有敘事理由，不堆無目的粒子、滑鼠尾巴、旋轉與重複淡入。
- 檢查至少兩類實際情節變化，例如主角移動並被前景遮擋、場景切換並帶入新物件狀態、
  或選擇改變路徑後抵達不同結果。不要把每幕都實作成同一張圖的縮放曲線。
- 使用函式庫時查官方文件與授權，清除 observer、listener 與動畫；不疊兩套平滑捲動。

## 操作底線

- 不攔截 wheel／touch 強迫逐幕播放；PageDown、方向鍵、空白與 Tab 正常使用。
- 第一屏提供略過故事與直達目的連結；章節導覽用真 anchor／button。
- 尊重系統 `prefers-reduced-motion`，另有可見動態開關且切換即生效。關閉後無 parallax、
  連續縮放、平滑捲動或 pin 阻塞，內容正常排列。
- 聲音預設關閉、使用者主動開啟；無聲也能完成任務。
- JS 載入或執行失敗仍可讀文字、圖片與連結，不先把全頁 `opacity:0`。
- 手機減少圖層、縮短 sticky，必要時逐幕靜態圖；沒有橫向溢出。
- 文字對比穩定、焦點可見；裝飾不搶讀屏或 pointer events。持續自動移動提供暫停，
  章節改變不反覆用 aria-live 朗讀整頁。

按 [驗收清單](website-quality.md) 在瀏覽器逐幕取證，包括轉折、結果與倒帶。至少測約
390px 手機與 1440px 桌面、鍵盤、200% 縮放、減少動態及無 JS。CSS 有 media query、
動畫時間軸存在或程式測試通過，都不能代替實際畫面的故事驗收。

效能依 [Core Web Vitals](https://web.dev/articles/vitals) 良好門檻：LCP ≤ 2.5s、
INP ≤ 200ms、CLS ≤ 0.1，實際使用者第 75 百分位評估。本機 Lighthouse 是實驗室數據，
沒有現場資料就標明，不能偽造 CWV 通過。
沒有效能追蹤或量測資料，不宣稱「穩定 60 FPS」或「所有手機流暢」。
